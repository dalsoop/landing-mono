# 풀지 못한 문제

## 사이트 폴더의 작업용 문서가 공개된다

- 증상: `https://cualign.external.kr/README.md`가 200으로 열린다(2026-09-30 확인). 같은 방식으로 `apps/cualign/docs/README.md`도 `/docs/README.md`로 열린다. 둘 다 한국어 작업 메모이고, 소개 페이지 방문자에게 보일 의도로 쓴 파일이 아니다.
- 영향: 비밀 값은 없고 저장소도 공개라 유출은 아니다. 다만 사이트 폴더에 두는 모든 파일이 공개된다는 사실을 모르는 사람이 내부 메모를 넣으면 그대로 운영 사이트에 올라간다.
- 지금 풀지 못하는 이유: 배포 워크플로에서 `README.md`, `AGENTS.md` 같은 파일을 빼는 코드 변경이 필요하고, 사이트 README를 폴더 밖으로 옮길지는 소유자가 정할 일이다.
- 가능한 방법: build 단계에서 `dist/<사이트>/`의 `README.md`, `AGENTS.md`, `docs/README.md`를 지운다.

## 양식 스팸을 허니팟 하나로만 막는다

- 증상: `Origin` 헤더를 직접 넣는 스크립트는 `website`를 비워 두기만 하면 `POST /_forms/demo-request`에 제한 없이 제출할 수 있고, 제출마다 R2 객체가 하나씩 생긴다.
- 영향: 가짜 데모 요청이 운영자의 수동 검토 목록을 채우고 R2 저장량이 늘어난다.
- 지금 풀지 못하는 이유: 속도 제한(Cloudflare Rate Limiting 규칙이나 Turnstile)을 붙이려면 Cloudflare 계정 설정과 코드 변경이 함께 필요하고, 어느 방식을 쓸지 소유자가 정해야 한다.
- 가능한 방법: `/_forms/*` 경로에 zone 수준 속도 제한 규칙을 걸거나, 요청 페이지에 Turnstile을 붙이고 `forms.js`에서 토큰을 검증한다.

## 양식 기록의 보존 기간이 없다

- 증상: R2 `landing-forms`의 기록은 운영자가 지울 때까지 남는다. 요청 페이지의 개인정보 안내에도 보존 기간이 적혀 있지 않다.
- 영향: 이름, 이메일, 소속 같은 개인정보가 목적(데모 접속 정보 발송)을 이룬 뒤에도 무기한 쌓인다.
- 지금 풀지 못하는 이유: 보존 기간은 소유자가 정할 정책이고, 정한 뒤에는 R2 수명 주기 규칙 설정과 안내 문구 변경이 함께 필요하다.
- 가능한 방법: R2 버킷에 접두어별 만료 규칙을 두고 같은 기간을 "How we handle your request"에 적는다.

## 삭제 요청의 신원 확인이 약하다

- 증상: 기록 삭제는 "같은 이메일로 다시 제출"하는 방식이라, 남의 이메일을 적어 삭제 요청을 보내는 것도 가능하다. 삭제 요청 자체도 새 기록으로 저장된다.
- 영향: 운영자가 확인 없이 지우면 다른 사람의 요청이 사라지고, 확인 절차가 없으면 삭제 요청 기록만 쌓인다.
- 지금 풀지 못하는 이유: 확인 절차(답장 확인 등)를 정하는 운영 정책 결정이 필요하다.
- 가능한 방법: 삭제 전에 그 이메일로 확인 메일을 보내 답장을 받은 뒤 지우는 절차를 운영 문서와 안내에 적는다.

## 외부 CDN 스크립트에 무결성 검사가 없다

- 증상: `hero3d.js`의 three.js ES 모듈 import와 `apps/cualign/docs/index.html`의 marked, DOMPurify `<script>`에 SRI(`integrity`)가 없고 Content-Security-Policy도 없다.
- 영향: cdnjs가 변조된 파일을 내보내면 방문자 브라우저에서 그대로 실행된다. 문서 뷰어는 DOMPurify가 변조되면 Markdown 정리도 무력해진다.
- 지금 풀지 못하는 이유: 모듈 import에는 `integrity`를 직접 붙일 수 없어 import map이나 자체 호스팅으로 구조를 바꾸는 코드 변경이 필요하다.
- 가능한 방법: `<script>`에는 `integrity`와 `crossorigin`을 붙이고, three.js는 사이트 폴더에 사본을 두거나 import map의 `integrity`를 쓴다.

## 기존 서브도메인과 같은 이름의 사이트가 어떻게 동작하는지 확인되지 않았다

- 증상: README는 "이미 레코드가 있는 서브도메인은 그 레코드가 우선이라 같은 이름의 폴더를 만들면 사이트가 열리지 않는다"고 적었다. 그런데 배포는 그 이름으로 Worker 라우트 `<이름>.external.kr/*`를 만들고, Cloudflare Worker 라우트는 프록시된 호스트의 요청을 DNS 레코드와 관계없이 가로챌 수 있다. 2026-09-30에 `cdn`, `immich`, `postiz`, `cualign-proto`, 존재하지 않는 이름 모두 같은 Cloudflare 프록시 주소로 풀렸다.
- 영향: README와 반대로 동작하면 폴더 하나로 기존 서비스(`immich`, `cdn` 등)가 이 저장소의 404 페이지로 바뀐다.
- 지금 풀지 못하는 이유: 운영 중인 서비스 이름으로 시험 배포를 해야만 확인할 수 있어, 소유자의 결정 없이 실험할 수 없다.
- 가능한 방법: 배포 워크플로에 금지 이름 목록을 두고 걸리면 실패시키거나, Cloudflare API로 기존 레코드·라우트와의 충돌을 배포 전에 검사한다.

## PR 단계 자동 검사가 없다

- 증상: GitHub Actions에는 `main` 배포 잡만 있다. PR에서 사이트 이름, `index.html`, `forms.json` 형식, JavaScript 문법, llms 파일 동기화를 검사하는 잡이 없고, `main` 브랜치 보호 규칙도 없다(2026-09-30 GitHub API 확인).
- 영향: 규칙을 어긴 변경이 합쳐지면 그 자리에서 운영 배포가 실패하거나 깨진 페이지가 곧바로 공개된다.
- 지금 풀지 못하는 이유: 새 워크플로 추가와 브랜치 보호 설정이 필요하고, 브랜치 보호는 저장소 소유자의 결정이다.
- 가능한 방법: 로컬 검사 명령을 그대로 `pull_request` 워크플로로 옮기고, `main`에 그 검사를 필수로 건다.

## 사이트 README의 설명 일부가 코드와 다르다

- 증상: `apps/cualign/README.md`는 `app.js`가 "히어로 처방 입력 타이핑"을 한다고 적지만, 커밋 `448093e`(2026-09-28)에서 히어로의 처방 입력 블록과 그 스크립트가 빠졌다. 지금 `app.js`의 타이핑은 에이전트 대화 데모에만 있다.
- 영향: README를 믿고 작업하는 사람이 없는 요소를 찾거나 되살리려 한다.
- 지금 풀지 못하는 이유: 사람이 관리하는 소개 문서의 문구라서 소유자가 고칠 문장을 정해야 한다.
- 가능한 방법: README의 `app.js` 설명에서 "히어로 처방 입력 타이핑"을 지운다.

## cualign 페이지 내용이 cuAlign 저장소의 현재 상태와 맞는지 확인되지 않았다

- 증상: 랜딩 문구, `apps/cualign/docs/*.md`의 명령과 출력 예시, `hero-case.json`은 모두 cuAlign 저장소(`dalsoop/nvidia-hackaton-2026-one`)의 2026-09-28 무렵 상태에서 옮겼다. 이 저장소에는 그 저장소와의 동기화 검사가 없다.
- 영향: cuAlign의 기능이나 한계가 바뀌면 페이지가 없는 기능을 약속하거나 이미 풀린 한계를 계속 적는다. 연구용 프로토타입 고지와 관련된 문장이 틀리면 방문자가 임상 사용 범위를 오해할 수 있다.
- 지금 풀지 못하는 이유: 원본이 다른 저장소에 있고, 대조하려면 그 저장소의 코드를 받아 예시를 다시 실행해야 한다.
- 가능한 방법: cuAlign 저장소에서 릴리스할 때마다 문서 예시를 다시 실행하고 `updated` front matter와 llms 파일을 함께 갱신한다.
